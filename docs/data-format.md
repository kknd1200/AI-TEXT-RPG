# 구형 안드로이드 게임 에셋 포맷

피처폰 게임을 `libjccvt.so`(모바일 VM 에뮬레이션)로 감싸 안드로이드로 옮긴 부류의
APK에서, `assets/` 안에 든 데이터 파일이 어떤 구조인지 역분석한 기록이다. 네이티브
안드로이드 게임이 아니라 포팅판이라 리소스가 피처폰 시절 포맷 그대로 남아 있다.

`tools/extract_apk.py` 가 이 문서대로 파일을 읽는다.

> 이 문서는 파일 **구조**에 대한 기록이고, 특정 게임의 데이터 자체는 이 저장소에
> 들어 있지 않다. 추출한 결과물은 원저작자의 저작물이므로 배포하지 않는다.
> 이 프로젝트가 실제로 쓰는 도감은 `tools/generate_roster.py` 가 만든 오리지널이다.

## 파일 종류

| 확장자 | 개수 | 내용 |
|---|---:|---|
| `.fbm` | 495 | 비트맵 |
| `.ani` | 407 | 애니메이션 |
| `.mif` | 149 | 맵 |
| `.cht` | 126 | 대사 스크립트 |
| `.mdt` | 125 | 맵 부가 데이터 |
| `.qst` | 102 | 퀘스트 스크립트 |
| `.ogg` | 52 | BGM / 효과음 |
| `.dat` `.fxt` | 13 | 아이템·몬스터·텍스트 테이블 |

문자열 인코딩은 전부 **CP949**다.

## 컨테이너

`.dat` 파일은 전부 같은 컨테이너를 쓴다.

```
[u8  count]
[u32 offset × count]      ← 리틀엔디언, "파일 선두" 기준 절대 오프셋
[records ...]
```

레코드의 끝은 다음 레코드의 오프셋이고, 마지막 레코드의 끝은 컨테이너의 끝이다.
중첩 컨테이너(`item_basic.dat`의 카테고리, `item_attr.dat`의 등급별 항목)도 같은
구조인데, **오프셋이 중첩 블록 기준이 아니라 여전히 파일 절대 오프셋**이다.
이 점을 놓치면 첫 하위 레코드부터 어긋난다.

## 문자열과 스탯 목록

```
문자열:   [u8 length][CP949 bytes]
스탯목록: [u8 count][(u8 statIndex, u16 value) × count]
```

`statIndex`의 순서는 `STR, DEX, MSTR, INT, CON, SPD`다. 게임 내 도움말 텍스트의
상태창 항목 순서와 같고, 속성별 특화 스탯이 실제로 그 자리에서 최고값을 갖는 것으로
교차 검증했다(물리 공격형 속성은 index 0, 속도형은 index 5가 최고값).

## 레코드 구조

### `item_mon.dat` — 몬스터 132종

```
[문자열 이름]
[u8  0x01]            레코드 타입
[u32 itemId]          전역 아이템 ID
[문자열 "스킬명/스킬설명"]
[u8  grade]           0=common … 5=god
... (미해석 필드)
```

### `item_stts.dat` — 몬스터 기본 스탯 132종

```
[문자열 "속성-등급"]   예: "수-common"
[u8  0x01]
[u32 itemId]
[u8  예약]
[u8  grade]
[u8  예약 × 7]
[스탯목록]            레벨 1 기준 기본 스탯
```

`item_mon.dat`와 `item_stts.dat`는 **인덱스가 1:1로 대응**한다. 두 파일의 레코드 수가
같고, 각 레코드에 들어 있는 등급 값이 서로 일치하며, 몬스터 이름이 풍기는 속성과
`item_stts.dat` 쪽 "속성-등급" 문자열이 맞아떨어지는 것으로 확인했다.

### `item_attr.dat` — 속성 × 등급 보정치

```
[문자열 "속성스텟-<속성>"]
  [중첩 컨테이너]
    [문자열 등급명]
    [u8 예약 × 8]
    [스탯목록]
```

### `item_skill.dat` — 패시브 스킬 66종

이름이 같은 레코드가 연달아 2~3개 들어 있다(등급 단계로 보인다). 설명 문자열은
묶음의 첫 레코드에만 붙는다.

### `item_basic.dat` — 아이템

최상위 레코드가 카테고리(`소비형아이템` 38, `장비아이템` 72, `재료아이템` 30,
`몬스터볼아이템` 7, `퀘스트아이템` 22, `캐시아이템` 24, `포획된몬스터볼아이템` 6)이고,
그 안이 다시 중첩 컨테이너다.

### `.fxt` / `.nm` / `.sub` — 텍스트 묶음

도움말 · UI 메시지 · 퀘스트 목록 · NPC 이름 같은 문자열 묶음이다. 길이 접두어 없이
CP949 문자열과 제어 바이트가 섞여 있어, 이 저장소에서는 CP949로 디코딩 가능한
구간만 훑어 뽑는다.

## 해석하지 못한 것

- 게임 로직 전반. 상성 배율표 · 데미지 공식 · 성장 공식 · 포획 확률은 데이터가 아니라
  변환된 VM 바이트코드 안에 있어서 텍스트로 남아 있지 않다. 이 프로젝트의 계산식은
  전부 새로 정한 것이다(`docs/design.md`, `data/rules/balance.json`).
- `item_mon.dat` 레코드 후반부의 u32 필드(스프라이트 ID로 추정)와 kv 목록.
- `.mif`(맵), `.cht`/`.qst`(스크립트), `.ani`/`.fbm`(그래픽).
